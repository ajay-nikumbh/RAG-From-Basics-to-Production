## 2. Human Evaluation (Appendix B)

- Annotators saw two generated clues, A and B, and picked the better one for factuality (and specificity).
- To avoid position bias, which model was A and which was B was randomized per example.
- Annotators were encouraged to research the topic on the internet and had detailed instructions with worked examples.
- Gold sentences were mixed in to check annotator quality. Two annotators who performed poorly on these were removed.

## 5. Null Document Experiment (Appendix F)

**Problem**: sometimes no retrieved passage is useful. Should the model be able to say "use no document"?

**Idea (from REALM)**: retrieve k documents, then add one extra empty "null document" with its own score, and marginalize over k + 1 options. Three ways to score the null document were tried:

1. Learn an embedding vector for the null document.
2. Learn a static bias term.
3. Use a neural network to predict its score.

**Result**: none of them improved performance, so the mechanism was dropped. On MS-MARCO, where useful passages often cannot be found, the model learned by itself to retrieve a particular fixed set of passages for questions that do not benefit from retrieval, effectively ignoring retrieval in those cases.

This "should we retrieve at all" question returns later in Self-RAG and Adaptive RAG (folders 08 and 10).

Notes:

- The paper counts 626M trainable parameters (110M + 110M + 406M). Since the document encoder is not trained, the parameters actually updated are 110M + 406M = 516M; the 626M figure includes the document encoder.
- The paper says the index holds 21M "728 dimensional" vectors, 15.3B values in total. 21M x 728 does give 15.3B, so the arithmetic matches, but BERT-base outputs **768** dimensions (21M x 768 is about 16.1B). 728 is very likely a typo for 768 that was carried into the calculation.
- The vectors can be stored in 8-bit floating point to save memory and disk.

## 7. Retrieval Collapse (Appendix H)

In early experiments on tasks such as **story generation**, the retriever "collapsed": it learned to return the **same documents for every input**. Once that happened, the generator learned to ignore the documents, and RAG performed the same as plain BART.

Possible reasons given by the authors:

- The task needs less explicit factual knowledge.
- Long target sequences may give the retriever less informative gradients.

```mermaid
flowchart LR
    A[Task needs little factual knowledge] --> B[Weak gradient signal to retriever]
    B --> C[Retriever returns same docs for all inputs]
    C --> D[Generator learns to ignore docs]
    D --> E[RAG behaves like plain BART]
```

Lesson for practice: retrieval helps knowledge-intensive tasks; for creative or open-ended tasks it may add little.

## 8. Key Points to Remember

- QA used greedy decoding with 15 (Token) or 50 (Sequence) documents; generation used beam size 4 with 10 documents.
- The full Wikipedia index needs about 100 GB RAM, or 36 GB compressed.
- About 626M trainable parameters (as reported) beat an 11B closed-book model.
- A null document did not help, and retrieval can collapse on tasks that do not need facts.
